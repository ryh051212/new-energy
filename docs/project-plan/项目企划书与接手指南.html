    1 先建立对项目的整体认识#

    1.1 用一次实际操作理解项目#

    ① 打开首页，查看魏都区边界与充电站
   App.vue → MapView.vue → FastAPI → PostGIS → GeoJSON → 地图
↓
② 点击“空间供需”，查看需求、站点数量与失配
   读取网格统计 → 展示专题和四象限 → 找到值得调查的区域
↓
③ 点击“约束选址”，选择时间场景、权重和建设约束
   功能区与需求模型 → 候选筛选 → 评分与补点收益排序
   ├─ 资料缺失 → 保留未知；开启对应硬约束时不通过
   └─ 候选通过 → 在地图定位，检查参照站和待核查条件
↓
④ 把候选纳入草稿，进入“方案推演”
   新增或模拟移除站点 → 调整桩数和功率 → 点击分析
   ├─ 数据或配置不合法 → 提示原因，结束本次运行
   └─ 计算成功 → 对照模拟前后服务、公平性、分流与建设条件
↓
⑤ 查看“车网协同”和“双碳评估”
   同一供给方案 + 可编辑参数 → 逐时负荷、光储、充电减排情景
↓
⑥ 导出结果，记录参数、判断与下一轮修改
   CSV 是分析结果；地图草稿不会写进正式站点数据库

    你应当能够回答三个问题：哪里值得调查？同样配置加在哪里更有帮助？结论依赖哪些数据和假设？ 这比只记住按钮名称更有用。

    1.2 企划目标与交付边界#

    目标 当前实现 接下来需要你的参与
    看清分布 站点、住宅、商业、设施目录与网格专题 抽查点位、分类、地址和坐标是否可信
    找到候选 时间需求、功能区、评分、间距和建设约束 说明权重理由，补充泊位与配变调查
    比较方案 全区及定位周边新增、移除、服务对照 设计有意义的方案和对照组
    评价影响 2SFCA、薄弱端、公平性、需求分流 手算小例子，做参数敏感性实验
    检查扩展情景 投资、24 小时负荷、光储、使用阶段 CO₂ 用有来源的输入替换示例参数
    形成可复现成果 模型测试、CSV、数据核查报告 保存参数、截图、版本与验收记录

    当前系统适合课程项目、方法演示和方案比较。真实建设决策还需要用地、消防、交通进出、供电接入、公众开放、实际车流及运营资料；界面中的模型得分不能代替这些调查。

    1.3 功能状态必须这样区分#

    功能 状态 应如何描述
    地图、POI 搜索、图层、定位、测距 已接入当前主页面 有正式 API，也有明确的失败处理
    空间供需、约束选址、布局推演 已接入当前主页面 使用空间数据和可解释规则计算
    车网协同、投资、双碳 已实现情景测算 输入包含假设，未接入实时调度或订单
    实时空闲枪数、排队、真实经营预测 未形成实时数据链 演示属性不作为实测结论
    AI 需求预测、AI 决策解释、历史时间分析 建设中占位 没有已训练预测模型或历史序列支撑
    Cesium 三维可视化 建设中占位 当前主地图使用 MapLibre 二维地图
    旧车主充电页、路线推荐、三维演示代码 前端已下线或归档 后端部分接口保留，不能算作当前主页面功能

    2 技术工具分别负责什么#

    2.1 从浏览器到数据库#

    ① 浏览器中的 Vue 界面
   页面组件收集输入，composable 保存交互状态，model 计算结果
   ├─ MapLibre GL：地图 sources 存数据，layers 决定颜色和图形
   ├─ Turf：前端点面判断、距离、缓冲区、裁剪、Voronoi
   └─ 图表：当前组件内 SVG / HTML 等实现；ECharts 仍在依赖中
↓ HTTP 请求 /api
② Vite 开发或预览代理
   默认把 /api 转交 http://127.0.0.1:8000
↓
③ FastAPI 后端
   参数校验 → 登录相关处理或业务查询 → psycopg2 执行参数化 SQL
↓
④ PostgreSQL + PostGIS
   空间表、属性、坐标、网格统计、空间关系
↓ JSON / GeoJSON 响应
⑤ Vue 更新状态 → 模板更新；地图通过 source.setData 更新图形

    选址评分、2SFCA、方案影响、负荷和碳计算主要在浏览器的 models/ 中完成。后端负责提供数据、数据导入维护和部分空间查询。点击“分析方案”不会调用一个 AI 模型接口。

    3.1 三类文件和一套正式数据库#

    ① 原始采集：data/raw 和离线脚本
   高德 POI 等记录 → 保留来源与原始坐标
↓ 清洗、去重、坐标转换、边界过滤

③ PostgreSQL / PostGIS 正式表

↓ FastAPI
④ 前端读取 GeoJSON，再进行显示与情景计算

public/geojson 是离线样本与预处理文件
└─ 当前主地图读 /api，并非失败后自动切换到这些文件

    本次在 2026 年 10 月 23 日直接读取离线文件得到：边界 1 个要素、站点 52 个、住宅 POI 225 个、商业 POI 200 个、六边形 170 个。这是离线样本数量。 本次连接本机数据库返回 OperationalError，未取得实时表数量；不能据此断言线上或本机现有数据库也只有 52 个站点。

    3.2 数据表和返回数据形态#

    表或资料 核心内容 页面用途
    weidu_boundary 行政边界面 区域过滤、定位和裁剪
    stations ID、名称、地址、状态、几何和站点属性 站点展示、供给配置
    residential_pois 住宅样本点 基础居住需求与空间分配
    commercial_pois 商业样本点 基础商业需求与空间分配
    hex_grid 网格及数量、标准化指数、四象限 基础专题与情景模型输入
    facility_pois 12 类设施目录、采集时刻、来源 设施图层、补充活动因子
    facility_grid_counts 视图 停车、工作、医院、学校、休闲等逐格计数 规划因子，不等于实测人口或车辆
    station-verification.json 字段核对状态与来源 解释哪些站点属性经过资料核对
    station-equipment.json 设备组、桩数、枪数、额定功率与来源 提供有证据的配置能力
    station-access-guides.json 车行入口及进场线索 站点详情，历史路线目的地处理

    数据库常用下划线字段，前端使用驼峰字段，例如 station_count → stationCount。接口负责转换。修改字段时必须检查 SQL 查询、后端序列化、前端模型、组件与测试五处。

    地图基础接口返回类似下列结构。以下是教学示例，坐标和数值不对应实际站点。

    {
  "type": "FeatureCollection",
  "features": [{
    "type": "Feature",
    "geometry": {"type": "Point", "coordinates": [113.85, 34.04]},
    "properties": {
      "id": "example-1", "name": "教学示例站",
      "isSynthetic": true, "totalCount": 2, "powerKw": 60,
      "simulatedFields": ["totalCount", "powerKw"]
    }
  }]
}

    POI 搜索是例外：/api/pois 返回对象数组，由 searchPois() 转成 Feature。不要把所有 API 都按 FeatureCollection 解析。

    3.3 真实地点也可能带演示属性#

    标记或情况 含义 检验方式
    isSynthetic=true 整个站点是虚拟演示记录 不写成实际存在的设施
    isSynthetic=false 且 simulatedFields 非空 地点是原有记录，部分属性是演示补全 按字段检查，而非一概当真
    未知数字为 null 或留空 尚未掌握 保留未知，不能填 0 或随意补值
    数字确实为 0 已知零值 需与未知区分
    有来源设备资料 可引用的配置记录 核对来源、资料时期和核对日期
    有采集时间 表示记录时间 不自动等于现场核验时间或实时状态

    “只看已记录点位”会排除虚拟地点，不会自动把真实地点的演示属性变成实测值。来源证据、核验时间、演示字段与设备资料仍需分别检查。

    设备模型优先使用有来源的 installedPowerKw；若存在设备资料对象但资料不完整，保持能力未知，不退回旧的演示 桩数 × 功率。没有设备对象时，才依据可用字段计算配置代理。最高单枪功率、设备额定合计、配变容量和实时可用功率是四种不同概念。

    入口：stationInformation.js、stationEquipment.js、station_equipment.py、facilityDemand.js 的 stationConfiguration()。

    3.4 坐标为什么一定要统一#

    ① 高德原始 POI 可能使用 GCJ-02
↓ 入库前做实际坐标转换
② 数据库正式 geom 和业务模型使用 WGS84 / EPSG:4326
↓ 前端持有原始业务坐标，距离和点面判断用这套数据
③ 使用高德街道底图时，toMapCoordinate / toMapGeoJSON 转成显示坐标
↓ 用户点图选址或测距
④ fromMapCoordinate 反算回 WGS84，再交给模型
↓ 切换底图
⑤ 从业务原始数据重新生成显示数据，避免反复转换累积误差

    给坐标贴上 SRID=4326 标签不等于完成 GCJ-02 到 WGS84 的转换。PostGIS 的 geography 距离以米计算；经纬度的差不能直接当成米。反向显示转换另外做三轮迭代修正。

    入口：coordinate_transform.py、spatial_migration.py、basemaps.js。

    4 应用如何启动以及登录如何发生#

    4.1 模块加载与每次页面实例不是同一件事#

    ① 浏览器载入 main.js
   静态 import 解析、加载依赖模块及样式；模块通常在当前页面会话中只求值一次
↓ createApp(App).mount('#app')
② 创建 App 实例，执行 App 的 <script setup>
   创建 route/user/loginOpen 等状态，创建 auth 会话控制器
↓ 首次渲染
③ 当前默认 route='/'，模板创建 MapView 实例
   MapView 的 setup 创建本实例状态、computed、watch、各地图工具
↓ DOM 挂载完成
④ MapView 的 onMounted 创建 MapLibre 地图
   App 的 onMounted 同时启动会话恢复和全局监听
   注意：地图 load 事件、会话网络响应相互独立，不保证谁先完成
↓ 地图 style 的 load 事件触发
⑤ 独立启动设施目录；Promise.all 并行请求五类基础数据
↓ await 基础数据全部成功
⑥ 过滤研究区、保存业务数据、更新地图 source、统计与边界视野
   ├─ 任一基础请求失败 → loadError 提示，finally 结束 loading
   └─ 成功 → loading=false，按当前路由应用视图

    6.2 网格归属与基础公式#

    ① 取站点、住宅、商业三类点，先过滤研究区内记录
↓
② 对每个点找覆盖它的网格
   ├─ 恰在共边上 → 最小网格 ID 优先，只归属一次
   ├─ 区内但边缘存在微小缝隙 → 可接受 5 m 内最近网格
   └─ 缝隙超过 5 m → 报错，不能悄悄漏计
↓
③ 按格计数 station_count / residential_count / commercial_count
↓
④ min-max 标准化 → 基础需求、供给、失配、四象限

    某类标准化数值 = (本格数量 - 全区最小数量) / (全区最大数量 - 全区最小数量)
若全区这一类最大值等于最小值，则该类标准化结果为 0

基础需求指数 D = 0.5 × 住宅标准化值 + 0.5 × 商业标准化值
基础供给指数 S = 站点数量的 min-max 标准化值
失配指数 M = D - S

需求高低以全区平均 D 为界，供给高低以全区平均 S 为界
等于平均值归入“高”组

    手算：若本格住宅标准化为 0.8、商业为 0.4，需求 D=0.6；站点标准化 S=0.2，则 M=0.4，表示这个相对尺度下需求偏高。四象限仍要再与全区平均比较，不能只看 M 正负决定类别。

    基础需求是相对代理指标，不是每日充电订单。站点数量供给也未区分快充、桩数和配置功率。有站网格占比 = 有站网格数 / 网格数；它不是服务半径覆盖率。

    离线 buildHexGrid.mjs 使用 Turf，六边形边长参数为 0.5 km。当前正式统计的归属校验在后端；不要为了修改展示直接重新运行历史生成脚本覆盖正式数据。

    7.2 功能区与时间需求算法#

    五类活动为居住、工作、购物、休闲、公共服务。功能区并非通过地点名称关键词识别，也没有接入土地利用分类模型。

    ① 读每格五类计数
   居住：residentialCount
   工作：workplaceCount
   购物：shoppingCount，缺时退回 commercialCount
   休闲：leisureCount，缺时退回 activityCount
   公共：publicServiceCount，缺时使用已知 hospitalCount + schoolCount
↓
② 每类强度 z(g,k) = 本格该类计数 / 全区该类最大计数
   缺失保留 null；已知全区最大为零时该类强度为零
↓
③ 本格活动份额 = 该类强度 / 本格各类强度之和
   ├─ 总强度为零 → 资料不足功能区
   ├─ 最大份额 >= 50% → 对应主导功能
   └─ 否则 → 混合功能
↓
④ 固定公共尺度 K = 全区各格“基础活动强度总和”的最大值
   当前场景需求 D(g,t) = Σ[z(g,k) × 活动系数(t,k)] / K
↓
⑤ 保留各活动的需求贡献，把需求分配给对应类别 POI
   无匹配 POI 时用标明的网格估计点；保持本格需求总权重不变
    时间场景 居住 工作 购物 休闲 公共
    工作日白天 0.35 1.00 0.55 0.35 0.75
    工作日晚间及夜间 1.00 0.15 0.80 0.80 0.45
    周末 0.70 0.25 1.00 1.00 0.65

    这些系数是可解释的实验设定。它们没有从历史充电订单训练得到，也没有被证明就是魏都区真实出行规律。交通枢纽类数据尚缺。多类别 POI 可具有多个活动标签；模型先确定逐格各活动总需求，再分配到相应位置，不额外生成车辆数。

    手算：某格居住强度 0.8、工作强度 0.2，其余已知为 0，则居住份额 80%，归入居住主导。若全区公共尺度 K=2，白天需求为 (0.8×0.35+0.2×1)/2=0.24，夜间为 (0.8×1+0.2×0.15)/2=0.415。两次都除以同一个 K，才有可比性。

    7.3 综合评分与硬约束#

    间距因子 G = min(最近可用参照站直线距离 / 1000 m, 1)
当前无可用参照站时 G = 1
停车因子 P = 停车场 POI 数 / 当前候选数据的全区最大停车场数
道路因子 R = 已提供的 0～1 道路条件值

综合评分 = 100 × Σ(有效权重 × 已知因子) / Σ有效权重
默认权重：需求 50、间距 25、停车 15、道路 10
需求为零 → 评分为零
需求未知或有效权重总和为零 → 评分未知

    例如 D=0.6、G=0.8，停车和道路未知：得分为 100×(50×0.6+25×0.8)/75=66.67。缺资料不是按零分处理，否则资料少会被错误惩罚。界面展示的有效权重比例是概览，逐行计算仍按该候选的已知因子确定分母。

    当前约束选址使用 scoreScenarioRows()。plannerPss.js 中还保留 planningScore() 及旧的快充、普通充电因子组合，不能把那套权重当成当前页面最终综合评分公式。

    控制项 当前初值 实际规则
    只看高需低供 关闭 开启后仅取该四象限
    与现有站最小间距 400 m 最近站距离达到阈值；这是可编辑假设
    最低偏好评分 1 分 包含等于门槛的候选；0 分可查看零分候选
    泊位硬约束 关闭，阈值 15 启用时停车资源、已知泊位和最少泊位都要满足
    配变硬约束 关闭 已知余量 kVA × 功率因数 >= 拟建总 kW
    功率因数 0.9 只做此情景的 kVA 到 kW 换算
    选址试算配置 快充、2 桩、每桩 60 kW 与沙盘直接新增初值不同
    批量数量 8，允许 1～20 按当前排序依次尝试；遇间距冲突跳过

    400 m 不是本地建设规范，停车场 POI 也不等于有 15 个公共可用车位。关闭硬约束时允许继续探索，但建设条件报告仍可显示待核查；开启后未知项无法通过对应筛选。

    7.4 默认排序不是只按评分#

    rankPlanningImpacts() 先把明确建设失败的候选排后。默认收益排序主要比较“新增可服务的需求权重”，再比较需求加权距离收益，最后比较综合评分；选择评分排序才主要按评分。界面同时比较当前场景与工作日白天默认权重，排名变化是在当前候选集合内计算的。

    批量方法是按当前顺序逐个选入、发现冲突就跳过的贪心规则。它不保证选出的多个站是全局最优组合，也没有进行遗传算法、粒子群、AHP 一致性检验或神经网络训练。修改评分会影响显示和门槛；如果收益排序仍然开启，排名未必随评分同步大幅改变。

    revision 是草稿版本号，resultRevision 是上次分析对应的版本号；两者不同即 dirty。这是防止“修改后仍把旧结果当新结果”的关键。

    9 两套空间算法怎样检验#

    9.1 Gaussian 2SFCA 评价可达服务#

    2SFCA 可以理解为“两步浮动搜寻”：先看每个站周围有多少竞争需求，再看每个需求位置可以获得哪些站的服务贡献。

    ① demandLocations 把逐格需求拆分到 POI 或网格估计位置
   每格分出去的权重之和保持等于原格需求；不是推算车辆数
↓
② stationConfiguration 读取站点能力和状态
   ├─ 已明确关闭/离线/不可进场 → 排除
   ├─ 能力未知 → 保留资料不足信息，不补功率
   └─ 能力已知且可用 → 参与能力分配
↓ 第一步，逐站计算
③ 在 1000 m 内按 Gaussian 距离衰减，累计该站竞争需求
   站点供需比 R(j) = C(j) / Σ[D(i) × W(d(i,j))]
   分母没有需求时不生成服务贡献
↓ 第二步，逐需求位置计算
④ 未截断可达能力 A(i) = Σ[R(j) × W(d(i,j))]
↓ 固定比较基准
⑤ B = 模拟前全区已知总能力 / 全区总需求权重
   服务指数 I(i) = 100 × min(A(i)/B, 1)
   ├─ B 不大于零 → 服务指数未知，不拿新增能力杜撰基准
   └─ B 有效 → 同一场景模拟前后都使用它
↓
⑥ 按需求权重汇总平均、薄弱端、公平性和定位依赖
   报告只评价模型能解释的部分

    服务半径 d0 = 1000 m
当 0 <= d < d0：
W(d) = [exp(-0.5 × (d/d0)^2) - exp(-0.5)] / [1 - exp(-0.5)]
当 d >= d0：W(d) = 0

W(0)=1；W(500 m) 约 0.7014；W(1000 m)=0

    这里的 1000 m 是本工具直线距离假设，不是已核实的步行时间，也不是魏都区建设规范。在阈值处权重为零；代码中另有简单距离覆盖字段使用 <=1000 m，所以不要把“距离在半径内”与“有正的能力贡献”当成完全相同的量。

    主要实现：facilityDemand.js 的 chargingDistanceWeight/demandLocations/stationConfiguration/compareChargingDemand；诊断实现在 facilityDiagnostics.js。项目注明参考 Zhang 与 Cao 2025 的可达性论文 DOI，当前具体公式、阈值、能力代理与比较规则以本项目代码为准。

    9.2 一个能手算的方案对照#

    设需求点 A、B 相距超过 2 km，各有权重 1。模拟前只有 A 处 1 个 60 kW 站；两点之间互相没有 1 km 内供给贡献。每个站与同位置需求点的 W=1。

    ① 基准 B = 60 / (1+1) = 30
↓
② 原方案
   A：单站竞争需求=1 → R=60 → A(A)=60 → 指数=min(60/30,1)×100=100
   B：没有供给 → A(B)=0 → 指数=0
   加权平均=50；薄弱需求占比=50%
↓
③ 在 B 处新增同样的 60 kW
   A、B 的未截断能力都为 60；固定基准仍为 30
   两点指数都为 100；加权平均=100；薄弱需求占比=0
↓
④ 如果把新站堆在 A 处
   A 未截断能力升至 120，但指数仍截在 100；B 仍为 0
   平均指数仍为 50，不能声称两地都受益

    这个例子说明：不能只比较站数增加了多少，也不能在模拟后改用新的总能力当基准重新打分。服务指数 100 表示达到本次比较的基准上限，不能读成真实需求 100% 满足。

    9.3 报告中的服务与公平指标#

    指标 计算与方向 需要避免的误读
    薄弱需求占比 指数 <50 的需求权重 / 总需求，越低越好 不是人口贫困率，也不是订单流失率
    薄弱端服务 按指数由低到高取最低 25% 需求权重的平均 不是最低 25% 网格简单平均
    服务不均衡程度 按未截断 A 和需求权重算加权 Gini，越低越均衡 全部无服务返回未知，不能写成完美均衡
    洛伦兹曲线 横轴累计需求权重，纵轴累计可达服务份额 横轴不是实测居民人数
    定位可达服务 在定位点累计附近站贡献，再按固定基准打分 依赖周边竞争需求和已知配置
    备用保障 去掉贡献最大的单站后剩余服务指数 主力站不一定是最近站
    主力站依赖 最大单站贡献 / 总贡献 不表示真实用户选择概率

    加权基尼可写为下面的可核对定义，代码使用排序前缀和减少运算量：

    G = Σi Σk [D(i) × D(k) × |A(i)-A(k)|]
    / [2 × (ΣD) × (ΣD×A)]

ΣD 或 ΣD×A 为零 → 未知
A=[60,0]，D=[1,1] → G=0.5
A=[60,60]，D=[1,1] → G=0

    补点方向提示会在不同需求位置独立尝试同样的 60 kW 新增配置，比较边际收益；它不是联合优化多个站，且此处的试探配置并不会自动随沙盘桩数改变。减点提示则每次独立撤去一个已知能力的原站，比较损失；低损失只能作为复核线索，不能直接建议关闭真实站点。

    9.4 固定需求分配模型解释补空缺与分流#

    这套算法回答“需求被谁分到”，与 2SFCA 的“各地点可获得多少相对服务”不同。

    ① createStationImpactContext 固定需求位置、权重与当前场景
   缓存的是距离，不是固定不变的分配答案
↓
② 对每个需求位置 i 找 1000 m 内能力已知的站
   吸引力 T(i,j) = C(j) × W(d(i,j))
↓
③ 分配给站 j 的需求权重 = D(i) × T(i,j) / Σj T(i,j)
   ├─ 无正吸引力 → 没有已知供给分配
   └─ 有正吸引力 → 各站分到的权重之和 = 原需求权重
↓ 模拟前后各算一次
④ 看新站得到的权重从哪里来
   ├─ 原来有已知服务 → 归为分流
   ├─ 原来无已知服务且无邻近未知能力站 → 归为补空缺
   └─ 原来附近有未知能力站 → 来源不确定
↓
⑤ 同时报告最近站距离、可选站址、原有站份额变化及建设条件

    手算：同一个需求位置权重为 10，原站 60 kW；新站也是 60 kW，两个站与该位置等距且在半径内。原站原先分到 10，新增后各分到 5。新站获得 5，其中全部来自分流；总需求仍是 10，不能说新增了 5 笔订单。这里的 10 只是教学权重。

    模型没有使用价格、排队、品牌偏好或真实路线时间，因此分配比例不能被当成经营预测。最近站距离的报告也可能涉及能力未知但位置已记录的站，解释时必须结合未知能力提示。

    实现：stationPlanImpact.js 的 allocate/evaluateStationPlan/evaluateCandidateImpact。建设检查使用 candidateFeasibility/evaluatePlanConstruction，逐项检查边界、站间距、公共可用泊位、配变余量、场地使用、车辆出入口和消防条件；多个新增点在同格时合计校核泊位与功率，防止各自通过但合计超额。

    9.5 模型局限与计算成本#

    两套模型使用同一研究区记录与当前需求情景，但不包含未收录的区外供给、道路阻隔、真实排队、设备共享限功率等完整机制。周边评价保留圈外的已记录站点，并不代表真实世界区外供给已经齐全。

    若有 N 个需求位置、M 个站，单轮主要需要 N×M 次距离或贡献运算；逐候选试算会再增加成本。当前模型在浏览器主线程运行，数据扩展后应先测量耗时，再考虑距离缓存、空间索引、Web Worker 或后端计算。现有 nextTick 和让出事件循环并不使计算自动变成后台线程。

    对应测试：facilityDemand.test.mjs、facilityDiagnostics.test.mjs、stationPlanImpact.test.mjs、combinedFacilitySimulation.test.mjs、facilityComparison.test.mjs、localChargingSimulation.test.mjs。

    10.1 从调整参数到曲线更新#

↓ 每小时同步计算

   ├─ 配变容量未知 → 仍可看负荷，不计算负载率和越限结论
   └─ 配变容量有效 → 计算负载率、越过警戒线小时数

    此处草稿配置变化会即时进入负荷情景，不要求先完成空间服务分析。空间报告的 dirty 与负荷曲线的即时更新是两套显示规则。

    10.2 负荷公式和参数#

    类型权重 q(k) = 输入相对权重 / 三类权重总和
类型充电负荷 L(k,h) = 已知配置总 kW × 并发系数 × q(k) × 类型形状(k,h)
充电总负荷 L(h) = Σk L(k,h)
光储调节前 beforeKw = 基础负荷 + L(h)
扣光伏后 netKw = max(0, beforeKw - 光伏功率)
最终 afterKw = netKw + 储能充电功率 - 储能放电功率

配变可用比较功率 T = 输入 kVA × 功率因数
负载率 = afterKw / T × 100%
警戒线 = T × warningRate

    beforeKw 是同一站点方案在光储调节前的负荷，不是“建设前站点负荷”。建设前后比较要看 baseline 与 profile，各自都有光储调节前后结果。越过警戒线也不必然等于超过配变额定容量：默认警戒比例是 80%。

    参数 初值 口径
    商业、办公、居住权重 45 / 25 / 30 自动归一化的假设结构
    充电并发系数 0.65 参与逐时峰值形状计算，区别于投资日利用率
    同范围配变容量 未知 必须与所汇总站点范围一致
    基础负荷 0 kW 示例值，需要调查替换
    功率因数、警戒比例 0.9 / 0.8 可编辑情景参数
    光伏装机 0 kW 日内用正弦形状；不是天气预报
    储能容量、功率 200 kWh / 50 kW 能量容量与每小时功率限制
    储能往返效率 0.9 充、放电各用其平方根

    三类形状是预设函数：商业约在中午和晚间两个峰，办公约在白天，居住约在 22 时形成跨午夜的峰。planningLoadProfile() 使用指数函数构造这些形状，光伏在白天用正弦形状模拟。这不是根据本地历史时序拟合的结果。

    10.3 储能如何保证能量守恒#

    ① 每次计算从储能电量 E=0 kWh 开始，每步为 1 小时
↓ h=0 到 23，逐小时推进
② 11～15 时：尝试充电
   充电功率 = min(功率上限, 剩余容量/充电效率, 警戒线下剩余功率空间)
   E下一时刻 = E当前 + 充电功率 × 1 h × 充电效率
   配变未知时不使用警戒线功率空间限制
↓ 其他时段不充电
③ 18～21 时：尝试放电
   放电功率 = min(功率上限, E当前×放电效率, 扣光伏后的负荷)
   E下一时刻 = E当前 - 放电功率 × 1 h / 放电效率
↓
④ 保持 0 <= E <= 储能容量，避免没有电也能放电

    小例子：若充、放电效率各约 0.9487，充入 10 kWh 后电池存约 9.4868 kWh；完全放出时最多向负荷提供 9 kWh，往返效率为 90%。代码不会凭空把 10 kWh 变成 10 kWh 再外送。

    储能按固定时段运行，可利用电网剩余功率空间充电，并非只吃光伏余电；未建立电价优化。午间充电可能增加负荷，全天峰值变化允许为负。代码中的“警戒线以上供能缺口”只是能量参考，尚未考虑完整储能功率约束，不能直接作为最优储能容量。

    当前没有接入车辆 V2G 反送电、台区拓扑、遥测、潮流计算或调度平台。因此车网协同应描述为“充电负荷与光储调节情景”。

    修改入口：PlannerGridCapacity.vue → plannerPss.js 的 configurationTotals/planningLoadProfile。验证：plannerPss.test.mjs 的逐时能量守恒、空资料和参数边界用例。

    11 投资与双碳怎样计算#

    11.1 新增站点投资情景#

    ① 用户在方案推演中编辑新增站配置
↓ PlannerScenarioAssessment
② configurationTotals 汇总新增点的桩数与配置 kW
↓ 用户调整日利用率、单车次电量、设备价、接电土建、毛利与运维
③ planningEconomics 计算新增方案的能量、服务量、投资和现金流
   ├─ 缺参数或参数无效 → 不生成有效结果
   ├─ 净现金流 <=0 → 保留数值，回收期未知
   └─ 投资与净现金流都 >0 → 给出静态回收年限
↓
④ 同样的计量侧电量交给共享碳模型 → 日、年使用阶段 CO₂ 情景
↓ 用户导出评估
⑤ CSV 写入参数与口径，便于复算

    日供电量 Q = 新增配置 kW × 24 h × 假设利用率
日服务车次估算 = Q / 单车次计量侧电量
投资概算 万元 = Σ(新增桩数 × 对应设备单价 + 每站接电土建费用)
年净经营现金流 万元 = Q × 365 × 单位毛利 / 10000 - 站数 × 年运维费
静态回收期 年 = 投资概算 / 年净经营现金流

    初值为日利用率 20%、单车次 24 kWh、快充设备每桩 8 万元、普通设备每桩 0.5 万元、每站接电土建 10 万元、单位毛利 0.3 元/kWh、每站年运维 2 万元。以上都是可编辑假设，尚未由报价、合同和实测运营证明。

    手算一座 2 桩、每桩 60 kW 的快充站：总能力 120 kW；日供电量 576 kWh；日服务量 24 车次；投资 26 万元；年净经营现金流 4.3072 万元；静态回收期约 6.04 年。这只验证公式，并非承诺有这些客户或能达到回收期。

    它只核算新增点，不计原站被分流的收入损失、拆除补偿、完整税费、融资和折现。空间分配的“需求权重”也没有自动换算为这些车次。投资表的日利用率 0.2 与负荷模型的并发系数 0.65，含义不同，不应强行统一成一个数字。

    入口：PlannerScenarioAssessment.vue、plannerPss.js 的 planningEconomics()。

    11.2 单次充电减排的执行流程#

    ① 用户打开“双碳评估”
   PlannerChargingCarbon 调用 useChargingCarbon，取得共享 settings
↓ 用户选择输入方式
② estimateChargingCarbon 验证效率、能耗、因子与电量
   ├─ 输入侧电量 → 乘充电效率，得到电池补电量
   ├─ 电池补电量 → 除充电效率，得到输入侧电量
   └─ SOC 变化 → 可用电池容量×SOC增量，先得到电池补电量
↓
③ 由电池补电量和百公里电耗换算同等行驶里程
↓
④ 对照汽油车同里程油耗×汽油燃烧因子
   本次电力排放=输入计量侧电量×所选电力因子
↓
⑤ 净减排=对照汽油燃烧 CO₂ - 本次充电电力 CO₂
   ├─ 正值 → 减排；负值 → 增排；近零 → 中性
   └─ 非法输入 → 展示错误，保留资料不足，不硬算
↓ 用户点击“记录本次估算”
⑥ createCarbonRecord 固定本次参数、时间和方法版本
   最多 100 条，保存本机；之后改当前参数不会改旧记录
↓ 导出
⑦ CSV 包含电量口径、结果、因子、来源和车辆参数

    E电池 = E输入 × η充电
同等里程 km = E电池 / 电池侧百公里电耗 × 100
汽油量 L = 同等里程 / 100 × 对照百公里油耗
汽油 CO₂ kg = 汽油量 × 汽油燃烧系数
电力 CO₂ kg = E输入 × 电力因子
净减排 kg = 汽油 CO₂ - 电力 CO₂

SOC 输入时：E电池 = 可用电池容量 × (目标SOC - 起始SOC) / 100

    11.3 一次充电的完整手算#

    示例初值：输入侧电量 24 kWh，效率 90%，电池侧电耗 15 kWh/100 km，对照油耗 7.5 L/100 km，河南 2023 年电力因子 0.5897 kg CO₂/kWh，参考汽油因子约 2.221059 kg CO₂/L。

    ① 电池补电：24×0.9=21.6 kWh
↓
② 同等里程：21.6÷15×100=144 km
↓
③ 对照汽油量：144÷100×7.5=10.8 L
↓
④ 汽油燃烧排放：10.8×2.221059≈23.9874 kg CO₂
↓
⑤ 充电电力排放：24×0.5897=14.1528 kg CO₂
↓
⑥ 净减排：23.9874372-14.1528≈9.8346 kg，界面约显示 9.83 kg

    本次直接核对了生态环境部2023 年电力二氧化碳排放因子表：河南 0.5897、全国 0.5306、华中 0.5271，与代码对应。它们是历史年平均，不是实时电网因子。

    汽油因子由代码中的 44.8×0.0189×0.98×(44/12)×0.73 换算；0.73 kg/L 是工具的参考密度假设。代码保留交通运输企业核算指南来源，不能将该计算结果说成官方直接发布的全国统一每升值。

    碳模型只比较使用阶段 CO₂，未包括整车、电池、设施制造、燃油上游及其他温室气体。充电器输出侧结算电量若不等于输入侧电量，需要先辨清计量位置。零电量应保留为零，负减排也应显示，不能为了好看截成零。

    入口：chargingCarbon.js 的 estimateChargingCarbon/createCarbonRecord → useChargingCarbon.js → PlannerChargingCarbon.vue。验证：chargingCarbon.test.mjs。

    以上是规划中的工作，不代表已经开发。优先使用一小批可信数据把方法验明白，再扩大规模。新增 AI 或更复杂的优化算法前，先确认输入、目标函数、约束和评价指标。

    17 常见问题与术语速查#

    17.1 遇到这些现象先检查什么#

    现象 优先检查
    有底图但没有业务点和网格 五类 API、数据库端口密码、loadError；底图和业务数据是两条链
    分析页一直要求登录 管理员配置、Cookie 主机与路径、服务重启、authorize 返回
    点位整体偏移 原始坐标系、入库是否真转换、是否在显示阶段重复转换
    权重变了排名似乎不变 当前是否仍按补点收益排序，候选集合是否相同
    某候选评分更高却不能纳入 间距、明确建设失败、泊位/配变和现有草稿冲突
    换场景后结果消失 旧空间分析失效，需要重算；草稿应仍保留
    只看已记录点位但仍显示模拟能力 原有地点的演示字段未被实测替换
    新增站很多但服务改善不明显 新站扎堆、指数上限、原有需求重分配或需求位置分布
    回收期显示未知 净现金流不大于零或参数无效，不应随便补一个年限
    无配变容量但有负荷曲线 允许算功率情景，负载率和越限保持未知
    本机补充资料另一端看不到 localStorage 的浏览器来源隔离，不是数据库同步
    单元测试通过但网页仍报错 检查真实 API、浏览器事件、坐标与外部服务；测试覆盖有边界

    17.2 一句话理解代码术语#

    词 本项目里的意思
    API 前端向后端请求数据的约定入口
    GeoJSON Feature 一个点、线或面及其属性
    FeatureCollection 多个 Feature 组成的数据集合
    source / layer 地图数据容器 / 地图绘制规则
    ref / reactive Vue 会跟踪变化的状态
    computed 根据已有状态派生出来的值
    watch 状态变化后执行的响应逻辑
    prop / emit 父组件传入数据 / 子组件向父组件发送事件
    setup 每次组件实例创建时执行的初始化逻辑
    onMounted 组件 DOM 挂载完成后的钩子，不保证网络完成
    nextTick 等待本轮 Vue DOM 更新完成
    onBeforeUnmount 组件销毁前释放资源的时机
    await 等待这一项异步结果；不等于全系统停止
    AbortController 取消请求或用信号让迟到结果失效
    WGS84 / GCJ-02 业务地理坐标与高德常用显示坐标体系
    POI 地点记录；样本数量不等于人口或车辆数量
    min-max 把同一批数量放到共同相对尺度
    情景 给定一组参数计算“如果这样，会怎样”
    MCDA 多因子加权评价，当前实现是可解释加权规则
    2SFCA 先按站计算竞争需求，再按地点汇总可达供给
    Gini / Lorenz 描述需求权重之间服务分布不均衡的量与曲线
    kW / kWh / kVA 功率 / 电量 / 视在功率，不能混用
    SOC 电池剩余电量百分比
    dry-run / apply 试运行并回滚 / 明确提交维护结果
    mock / integration 隔离模拟依赖的测试 / 连接真实服务的检查
